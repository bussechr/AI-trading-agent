## Bridge Contracts

- Cold API import keeps dataframe and migration tooling out of the bridge bootstrap: `live.policy` loads pandas and the session contract only when a pandas row or session timestamp is evaluated, while the provider catalog uses pandas only for static typing. Migration-head validation reads literal revision graph metadata without executing migration code; Alembic is launched only for an actual migration command. Importing `fxstack.api.app` alone does not load pandas, NumPy, or Alembic. Runtime clients import the dependency-free `api.protocol_identity` module for protocol negotiation; only API handlers and schema consumers hydrate Pydantic-backed `api.wire` models.
- `/v2/handshake`: public wire-version/build metadata. Protocol `v3.0.0` is the minimum compatible source-attested wire contract; BridgeEA requires an exact match before it polls commands or publishes authoritative broker truth, while the dashboard accepts compatible minor/patch drift
- `/v2/ready`: readiness, freshness, runtime startup progress
- `/v2/state`: full bridge state snapshot used by dashboard route, including
  current database health. The response joins the latest indexed decision
  snapshot for `agent_decisions`, `agent_diagnostics`, and `vol`; those bulky
  telemetry fields are not duplicated in the row-locked authority state.
- Bridge liveness normalization performs no hidden database reads. Routes that
  expose feature backlog or parity obtain raw runtime state and one exact
  metrics snapshot together in a single store transaction, then pass both into
  normalization. Nested and top-level feature observability therefore share
  one coherent snapshot, while lightweight `/v2/monitor`, workflow, and
  `/v2/readyz` consumers do not scan metrics tables.
- Every non-paper command ACK uses the same exact source-attested classifier at
  the durable-store boundary. A positive ticket alone cannot finalize a legacy
  or unmarked MT4 command; command identity, broker actuals, mutation state,
  and applicable economic bounds must agree, otherwise the row remains
  `reconcile_required`. Paper simulation is the only separate non-broker scope.
- `/v2/ready` reads one bounded command/event snapshot for both paper and live
  orchestration summaries. Its experiment, promotion, and approval evidence
  reads each return the exact table count and latest row together instead of
  fetching ten rows and then rescanning the same table for its count.
- Orchestration experiment and promotion APIs pair each bounded row read with
  its exact filtered count. Experiment lists load approvals and promotions for
  all returned experiment IDs in two partition-ranked queries, preserving each
  experiment's newest-first nested limit without per-item database reads.
- `POST /v2/market/tick`: authenticated MT4 quote transport. `received_at` measures HTTP delivery, while the raw broker `MODE_TIME` value is carried as an opaque `source_event_token` and must never be interpreted as UTC; the first token establishes a baseline and only a later token or quote change advances bridge-receipt market-event time
- `POST /v2/market/ticks`: bounded unique-symbol quote snapshot under one authenticated producer lease and one shared receipt clock. The bridge normalizes the complete batch first, persists changed broker events in one atomic executemany transaction, and only then publishes the corresponding in-memory quotes/history; a persistence failure therefore exposes none of the staged batch. Baselines and duplicate transport receipts still update memory without diluting durable market-event history.
- `GET /v2/market/ticks`: pair-scoped quote snapshots with separate `transport_fresh` and `market_event_fresh` evidence. The API server-stamps MT4 provider, canonical pair, IG venue, instrument, and transport receipt fields; a repeated EA timer post can keep transport live but cannot refresh market-event age
- `POST /v2/market/bars`: authenticated single-symbol completed-bar ingestion. `POST /v2/market/bars/batch` is the additive atomic multi-symbol form: one top-level leased market-source identity covers at most 64 unique normalized symbol/timeframe groups and 500 total rows, the server stamps one receipt clock for all newly accepted rows, and every schema, source, closed-bucket, first-receipt, and immutable-conflict check completes before shared history mutates. Any invalid or conflicting item rejects the whole frame; exact reposts retain their original receipt, HTTP 2xx means every row was accepted or idempotent, and the original single-symbol route remains compatible.
- `GET /v2/market/bars/coverage?symbol=<PAIR>&timeframe=M1&minimum=241`: lightweight authenticated direct-row coverage proof used only by MT4 recovery. It returns the exact source-bound total and trailing-consecutive direct-row counts plus the latest direct completed timestamp without transmitting the rows. `ready=true` requires either the trailing consecutive count to meet `minimum` or one authenticated full 241-row terminal snapshot whose post-snapshot tail remains consecutive; the latter prevents an authentic older no-tick gap from causing endless recovery while any newly missed edge invalidates the attestation. After an empty process-local API boot, the bridge returns exactly one authenticated `503 direct_m1_seed_recovery_requested` to the baseline EA's tick batch; the EA clears its retained bootstrap watermarks while the handshake stays compatible, and every subsequent tick is accepted normally. A terminal-only restart also compares the latest timestamp with MT4's exact shift 1 before reusing a seed. A non-200 or malformed coverage response retains progress for the next pass.
- The MT4 minute edge runs at 250 ms only from UTC `+1s` through `+4s`. Each callback checks at most four unresolved exact-scope symbols, stages their immutable shift-1 JSON across callbacks, and sends one atomic batch only after a full sweep or after all remaining rows are staged. Readiness requires broker `MODE_TIME`, exact `iTime(...,0)` and `iTime(...,1)`, then one final shift-1 `CopyRates` row and final `iTime(...,1)` agreement; `SERIES_LASTBAR_DATE` is not part of the hot path. Successful symbols are not rebuilt or resent. The bucket stays incomplete unless every configured symbol is accepted, and later throttled retries reconcile data without extending the separate five-second entry deadline.
- Command polling, lifecycle management, exact-scope ticks, heartbeat, reports, snapshots, recovery, and coverage checks stay behind the wrap-safe approximately-one-second lane. Remote coverage and cold recovery can begin only after `+7s` and before `+45s`; a ready coverage response returns immediately. Otherwise, at most one symbol per maintenance pass may enter recovery. The identity-bound cached broker symbol is passed directly into cold observation instead of rescanning MT4's full symbol catalogue. Because MT4 builds an off-chart `CopyRates` series asynchronously, the EA gradually opens or reuses one M1 chart for every configured strategy symbol outside the minute-edge guard and retains EA-owned chart IDs until deinitialization; this keeps shift zero/one rolling at the broker edge instead of rotating one late temporary chart. A successful three-row refresh must put shift zero in the broker `MODE_TIME` minute, while cold shift one need only be positive, minute-aligned, and older than shift zero so authentic no-tick gaps remain gaps. A coherent first 241-row fingerprint pins that symbol for its five-second recheck; hard-incoherent symbols advance immediately, and a repeatedly changing coherent snapshot is released after two pinned rechecks so no pair can monopolize the exact-scope cursor. Only a stable pair uploads its 241 rows, and it does so as one atomic 241-row request so the API can attest the terminal snapshot instead of seeing unrelated `100/100/41` chunks. The separate T+5 minute-edge path still requires the exact prior minute. When the next UTC minute supersedes an incomplete edge, successful per-symbol data watermarks remain intact, only unresolved symbols enter bounded recovery, and the scheduler bucket advances without an all-scope rebuild or a synthetic bar. A genuine multi-minute timer/wall-clock jump still requests bounded all-scope recovery because the one-row incremental contract cannot cover it. The first common transport/auth/server failure still aborts cold recovery for one minute. The downstream MTVCLC adapter demands 241 consecutive completed minutes unless the API holds an authenticated full terminal snapshot with a consecutive post-snapshot tail.
- Shift zero is always excluded. Direct EA rows carry exact MT4 bid `iOHLC`, strict integer `iVolume`, `price_basis=mt4_bid_ohlc_v1`, and `volume_source=mt4_ivolume_tick_count_v1` as one immutable provenance contract. A conflicting repost receives HTTP `409 completed_direct_mt4_bar_immutable_conflict` and commits nothing. Publication follows only MT4's finalized shift-1 state; a missing broker tick, clock correction, blocked timer, or slow loopback remains fail-closed latency rather than permission to synthesize a bar.
- `GET /v2/market/bars`: merged broker-history and live-tick bars consumed by runtime feature refresh. The API rejects a bucket until its timeframe has closed, owns its first authenticated `received_at_epoch`, preserves that value on exact repost, and exposes direct rows with MT4 provider, canonical pair, IG venue, source timeframe, and terminal source identity. A pre-contract row with no receipt remains unqualified. Tick-aggregated fallback bars are explicitly labeled `price_basis=bridge_tick_mid_ohlc_v1` and `volume_source=bridge_market_event_count_v1`; they must not be treated as MT4 `iVolume` bars
- `GET /v2/market/bars/batch?timeframe=M1&limit=242`: one authenticated, read-only exact ordered scope-v3 response for the 22 MTVCLC symbols. The route reads only the retained authenticated direct-MT4 bid/iVolume cache; tick-derived aggregation and fallback rows are excluded. The runtime preloads the 241-row baseline outside the entry window, then requests and merges a two-row tail from `T+3s` until every pair has arrived or the reserved `T+4.500s` evaluation margin begins. A pair still late at that boundary remains independently unavailable. The route returns no authority.
- The authority-free MTVCLC runtime adapter binds bar and quote rows to the same active singleton market-source ID and producer instance, filters the current incomplete M1 bucket, accepts exactly 241 consecutive completed rows only when `price_basis=mt4_bid_ohlc_v1`, `volume_source=mt4_ivolume_tick_count_v1`, and `volume` remains a strict integer, and requires the signal bar's raw server receipt to fall from its close through the inclusive five-second entry deadline. Evaluation itself must occur by that raw deadline, and a quote receipt after the trusted evaluation clock fails closed. The sealed pure strategy still floors a valid quote receipt to its preregistered whole-second observation clock. Mid/event-count fallbacks, cloned producers, stale or future transport, reordered scope, and XRPUSD fail closed before evaluation.
- `/v2/reports`: API-key authentication alone is diagnostic. Structured `heartbeat`, `bridge_status`, `symbol_specs`, `positions_snapshot`, and closed-trade reports become broker-authoritative only after their terminal producer identity claims the same singleton lease as poll/ACK. Each accepted truth report is stamped with the canonical market-source object/ID; lower-fidelity plain text cannot overwrite authoritative broker state
- `AGENT HOT PATH`: the 250 ms finalized-M1 lane checks the identity and shape of the already validated bar-symbol cache; configured-scope parsing and duplicate validation remain on the approximately-one-second off-edge maintenance lane. The 15-second `bridge_status` and `symbol_specs` reports reuse the identity-bound market-data mapping and its cached resolution diagnostics, while still resampling dynamic broker contract fields. Full `SymbolsTotal` catalogue discovery therefore occurs only during the bounded cache refresh/retry path, outside the protected minute edge, not twice for every one of the 22 strategy symbols on each report cycle.
- `/v2/commands`: enqueue or poll broker commands; direct live BUY/SELL enqueue is forbidden because entry authority is in-process and runner-owned. Poll and ACK use a dedicated command token rather than the general bridge API key and must renew the configured singleton consumer/terminal lease.
- `POST /v2/scalp/commands`: disabled compatibility surface; it always returns `403 scalp_live_ingress_disabled_unvalidated_authority`, imports no external scalp/research package, and has no command-queue path
- `/v2/commands/ack`: authenticated, idempotent terminal broker-outcome ingestion
- `/v2/commands/events`: ACK and delivery history
- `/v2/decision-snapshots`: persisted decision history for runtime audit and offline export

## Installed API Boundary

- Production starts the bridge directly as `python -I -m uvicorn fxstack.api.app:app --loop asyncio:SelectorEventLoop`. The explicit Windows selector loop prevents expected EA socket closes from becoming Proactor callback trace churn. The bridge never enters through a repository source-tree shim or a second service path.
- `fxstack.api.app`, `RuntimeService`, the command store, ACK ingestion, and provider adapters come from the same filtered non-editable runtime distribution as the decision runner, feature worker, monitor, and preflights.
- production scalp engine identity schema v3 measures this last mile: API/schema, provider, risk, DTO, store, service, startup, runner, strategy/control modules, signed-validation and legacy-readable authority handling, and the MQL4 `BridgeEA`, `BridgeHttp`, and `BridgeUtils` sources. Any measured-source change changes the installed engine identity and breaks the exact v5 sealed-engine/outer-v2 runtime-release match before another entry can be authorized; evidence-v3 remains the separately authenticated authority-free validation result
- The installer does not deploy raw `fx-quant-stack/src`. Training activation, mutable registry operations, research/backtest, replay/experiment, and alternate model loaders are physically absent from the API interpreter.
- The API accepts only artifacts and model identities prepared before deployment. It exposes no endpoint that trains, promotes, activates, rewrites the active manifest, or launches research.
- Shadow mode remains an optional command-admission posture of the one installed runner behind this API. The installed runner may select the model stack or `mtvclc`; MTVCLC remains IG-DEMO-only and requires a separately signed runtime release even when the broker account is demo. Every path shares this API, durable store, egress authority, command serializer, and MT4 consumer; the external research scalper remains excluded.

## Command Lifecycle

- the selected installed strategy resolves one canonical entry candidate, obtains an exact final risk-approved immediate-trade plan, and applies its production authority before submission; the model stack uses committee/governor rollout authority, while `mtvclc` binds `admission_mode=signed_validation` and `account_mode=demo` with generation, engine/config, outer release/evidence/revocation identities, exact venue/scope/cost/surface/execution hashes, boot, revision, and expiry
- invalid or revoked MTVCLC runtime-release material may continue to bridge/service access only as a protective-management candidate. That result is never entry authority: BUY and SELL remain hard-refused, and startup fails closed unless the later store-backed exact-owner protective activation succeeds. New entry admission is IG-DEMO-only and remains bound to explicit arming, the distinct signed runtime release, and fresh demo broker/account attestation.
- an immediate market BUY/SELL trade uses `RuntimeService.submit_approved_command` with an in-process `FinalEntryApproval` that binds canonical readiness, the risk-approved payload, committee/governor permission, production rollout state, pair, sleeve, side, trace identity, authority admission mode, the matching fresh broker account mode/scope, and the current monotonic live-authority revision. The runner treats absence of that exact service method as `approved_entry_submission_unavailable`, records no submission attempt, and never falls back to public `submit_command`. Every live MT4 entry includes the exact market/pending-forbidden selected-symbol broker contract and 20-point adverse-fill envelope; the production scalper additionally binds its deadline, broker-plan, protection-cushion, and signed strategy-authority fields. The final payload may only reduce approved lots or add transport metadata.
- model-stack live entry risk projects the authenticated selected-symbol broker contract from the same bridge state used for account admission. BUY binds the current ask and SELL the current bid, rounds the worst permitted fill conservatively on the broker tick grid, and sizes/evaluates reward-to-risk from that adverse price. One provider helper owns the common execution type, pending prohibition, quote/worst-fill geometry, contract identity, lot grid, point/tick, margin, and tradeability validation for both model-stack and MTVCLC serialization; MTVCLC layers only its stricter deadline, plan, cushion, and signed authority. BridgeEA parses both into the strategy-neutral `MarketEntryEnvelope` and applies `ValidateExactMarketEntryEnvelope` plus `ValidateMarketEntryPreSend` before ticket creation.
- the durable store independently rejects retired external/legacy standalone-scalp BUY/SELL commands and any `production_scalper` entry missing its exact current scalp-authority binding, including `admission_mode` and `account_mode`. Broker polling expires recognizable unattested queued entries and moves already-delivered entries to `reconcile_required` because broker outcome is unknown; exact-owner protective commands remain deliverable even when new-entry signed-validation authority has been revoked
- immediately before enqueue, `submit_approved_command` rereads bridge state and the store repeats the check atomically with insertion; runtime/admission/kill state, broker account mode/scope, authority-bound expected account/admission modes, and the exact authority revision must still match, and the heartbeat plus the command pair's persisted broker-event-time tick must be fresh
- production-scalper BUY/SELL also carries the exact versioned rollover-guard schema/config hash. The cycle, row-locked enqueue check, and broker-poll reauthorization independently reject entry during the fixed 20:20:00-22:10:00 UTC half-open blackout. From 20:50:00 the lifecycle emits the ordinary immediate-market exact-ticket `CLOSE` for every restart-joined owned position; blackout never suppresses exits and never introduces a pending order
- a production-scalper entry is re-priced at both enqueue and poll from one current database quote set. The store projects the authenticated scope-v3 exact-22 contract state onto the selected symbol, applies that symbol's current lot size/lot quantum/stop floor/margin, resolves the quote-to-account conversion from a fresh direct or inverse persisted tick when needed, and recomputes stop-loss cash risk against current equity. Lots may shrink after approval but the revalued risk may exceed neither the original approved cash amount nor the current budgeted equity fraction. Conversion crosses outside the exact 22 may be fetched and persisted only as market-data extras; they never enlarge strategy pair scope, live pair scope, or command execution scope
- every production-scalper BUY/SELL executes an immediate market trade: BUY at the current ask or SELL at the current bid. Proposal, qualification, broker plan, approval, command, durable payload, wire line, and EA envelope all carry `execution_type=market`, `pending_orders_forbidden=true`, and the same positive integer `entry_deadline_epoch`. MT4 internally names the native function `OrderSend`, but this boundary may call it only with `OP_BUY` or `OP_SELL`; pending-entry opcodes (`OP_BUYLIMIT`, `OP_SELLLIMIT`, `OP_BUYSTOP`, and `OP_SELLSTOP`) do not exist in this lane and must never be derived from a scalp command
- the risk payload retains the selected probability provenance. MTVCLC accepts only the signed evidence-v3 Wilson lower bound over the cumulative 4,874-cell family for the exact side/symbol cell; there is no demo-local probability or unsigned entry path
- the complete `fxstack.production_scalp_broker_entry_plan.v2` envelope survives risk, enqueue, poll, wire serialization, and EA parsing. It binds the immediate-entry triple plus logical/broker symbol, side, quote entry, approved worst fill, exact `max_slippage_points=20`, SL/TP, venue/account currency, contract schema/hash, lot size/min/step/max, point, price-unit tick size, digits, stop/freeze levels, margin requirement, and `trade_allowed`. Its SL/TP floor is checked directionally against current bid/ask—BUY SL below bid and TP above ask; SELL SL above ask and TP below bid—with exactly five protection-cushion points beyond the broker stop level; any omitted, changed, expired, off-grid, stale, or out-of-bound value is a ticketless pre-send refusal
- command egress is armed by the validated production runtime for its current boot and exact pair/sleeve/intent scopes. Twin/research release state may be present as advisory telemetry but cannot enable, disable, or delay command delivery
- signed-validation scalp activation rechecks the complete runtime-release witness under the authority-store lock: distinct release/evidence public-key identities, outer-v2 release certificate, signed registry chain, evidence-v3, exact v5 preregistration body/artifact and whole-engine binding, generation, installed engine/config, exact IG-DEMO venue/symbol scope, signed costs, all 44 qualification bounds, immediate-market/pending-forbidden execution contract, and effective expiry. Its persisted v3 authority binds those identities plus runtime boot and revision. There is no direct-demo entry mode and no real-account entry path. A fresh authenticated exact-22 broker-contract table with valid identity and geometry remains required; transient per-symbol `trade_allowed=false` does not revoke unrelated symbols, while the selected symbol must still be tradeable at sizing, enqueue, poll, provider dispatch, and EA entry.
- every production-scalper wire line carries the same 25 signed-v3 authority fields rechecked at enqueue and broker poll: schema, admission/account modes, generation, strategy/version, engine, config ID/hash, release certificate/key, evidence/key, registry generation/revision/hash, qualification surface, cost mapping, execution contract, expiry, venue, scope, authority binding, runtime boot, and authority revision. BridgeEA requires their exact MTVCLC/demo/schema/scope identities, generation agreement, positive revisions, live expiry, and valid SHA-256 shapes before it can execute an immediate BUY/SELL trade.
- when signed scalp evidence is invalid, the only admissible live fallback is a boot-bound protective-management plane backed by a structurally valid revoked prior authority. It must publish the scope-v3 exact ordered 22-pair scope, only the `scalp` sleeve and `EXIT` intent, and zero stage/budget; current venue/account/Magic attestation plus exact durable historical entry ownership and a successful entry ACK or fresh authoritative matching position are required, otherwise readiness and delivery fail closed
- immediately before broker delivery, the store reauthorizes every queued BUY/SELL against the current runtime/admission/kill state, exact admission/account-mode-bound authority revision, approved pair/intent, broker account identity, heartbeat, pair tick, market-only type, pending-order prohibition, and deadline in the polling transaction; after that potentially expensive check it resamples the server clock and repeats entry authorization before marking the row delivered, so work that crosses T+5 expires undelivered rather than creating a delivered-without-ACK uncertainty. Revoked, stale, superseded, expired, or legacy-unattested entries are expired with an audit event, while protective commands remain independently pollable. Enqueue caps durable expiry to `min(configured command TTL, entry_deadline_epoch - server_now)`, and the EA checks the same deadline again on every retry immediately before `OrderSend`
- public `RuntimeService.submit_command`, including direct `POST /v2/commands`, rejects live MT4 BUY/SELL with `403 final_entry_approval_required`; HTTP callers cannot manufacture the in-process approval
- standalone scalp research has no alternative approval token: live mode is invalid, its legacy client refuses locally, and the compatibility API cannot bypass `FinalEntryApproval`. Only the installed `mtvclc` strategy family can activate database-backed entry authority, and only for the attested IG-DEMO account after public verification of the separate signed runtime release
- in the normal live plane, non-entry commands continue through `RuntimeService.submit_command`; protective CLOSE, CLOSE_ALL, CLOSE_PARTIAL, and MODIFY_SL actions are not gated by the entry canary, although live intent scope and the ordinary runtime, queue, governance, reconciliation, broker protections, and broker-ticket ownership contract still bind them. The invalid-signed-evidence scalp protective-management plane is narrower: it accepts only exact-owner full `CLOSE`, never `CLOSE_ALL`, `CLOSE_PARTIAL`, `MODIFY_SL`, BUY, or SELL
- accepted managed `CLOSE_PARTIAL` and `CLOSE` commands carry `fxstack_lifecycle_command_context_v1` and enter pending partial/exit ledgers. Enqueue is intent persistence only: it does not increment partial history or mutate recent-exit, campaign-close/transition, or sleeve-outcome state
- management completion is broker-confirmed. Only an `acked` ACK whose post-mutation ticket actuals attest the complete command semantics commits the corresponding partial/exit; alternatively, only a newly received positions snapshot later than submission may prove the lot reduction or submitted position-signature absence. A stale or repeated snapshot cannot confirm an action
- terminal non-success rows receive no management credit. An undelivered expiry resolves immediately; other delivered/failed/reconciliation states resolve without credit only when a newer positions snapshot proves the broker lots or position remained unchanged
- any delivered, reconciliation-required, or previously delivered non-terminal command starts as an account-wide BUY/SELL fence. The store may contain that fence to the exact affected symbols only after a fresh version-current authoritative positions snapshot, bound to the current broker account scope, has both broker source time and bridge receipt time later than every uncertain transition. The possible exposure is then present in the book consumed by ordinary portfolio/margin controls: affected symbols remain quarantined, unrelated symbols may proceed, and missing-symbol or `CLOSE_ALL` uncertainty remains account-wide. The store repeats the symbol-aware check atomically at enqueue and poll, while CLOSE, CLOSE_ALL, CLOSE_PARTIAL, and MODIFY_SL remain admissible
- `protocol.command_to_mt4_line` serializes the MT4 wire line through the same cached selected-provider dispatcher used by `command_to_provider_line`; importing the protocol eagerly loads no execution adapter. Every MT4 BUY/SELL carries the complete exact market-entry envelope, a positive exact Magic, and a bounded comment-safe owner token derived deterministically from command/session/Magic identity and declares `ticket_owner_v1`; there is no bare or unmarked BUY/SELL compatibility serialization path. Paper commands never enter the MT4 serializer, and direct live HTTP entry remains rejected before serialization. The EA uses the owner token as `OrderSend`'s broker-comment prefix instead of the historical fixed `ELBridge`.
- after any BUY/SELL returns a positive ticket, BridgeEA selects that exact ticket and attests command, logical and broker symbol, side, market type, Magic, owner comment, lots, open price, SL, TP, and the adverse fill bound. Every confirmed entry ACK carries `fxstack.mt4_order_actuals.v1`; missing or mismatched actuals become `reconcile_required` instead of taking the retired generic positive-ticket success path.
- strict `CLOSE`, `CLOSE_PARTIAL`, and `MODIFY_SL` carry `target_ticket`, positive Magic, owner token, and `ticket_owner_v1`. Production-scalp exits additionally carry `managed_entry_command_id`, which must resolve the exact durable BUY/SELL row and its complete entry-time admission mode, expected account mode, generation, boot, admission identity, engine/config, venue/scope, Magic, and owner-token authority. Before any broker mutation the EA selects that one open market ticket and requires its logical symbol, `OrderMagicNumber()`, and `OrderComment()` owner prefix to match; a missing or mismatched identity is a terminal ticketless `not_attempted` refusal, never a symbol-wide fallback
- non-production legacy management without ticket identity is serialized only as `legacy_elbridge_v1`; its symbol scans and legacy `CLOSE_ALL` can touch only positions whose exact broker comment remains `ELBridge`. New owned entries never use that comment, so the compatibility path cannot manage the `production_scalper` lane
- after broker handling, the EA writes each JSON ACK to its pinned account/server + bridge-endpoint + Magic + producer-instance scoped `FILE_COMMON/FXStack/AckOutbox` directory, flushes it, closes it, and atomically promotes the temporary file before the first HTTP attempt; credentials are never embedded in ACK payloads or journaled EA inputs, and filenames include a hash of `TERMINAL_DATA_PATH` plus chart identity to avoid cross-terminal writer collisions
- after a positive entry ticket, MT4 performs `OrderSelect(ticket, SELECT_BY_TICKET, MODE_TRADES)` and reports versioned actual command ID, logical/broker symbol, side, `execution_type`, ticket, Magic, owner token/comment, lots, remaining lots, open/close state, open price, SL, and TP. Only a complete match to the market envelope is `acked`; selection failure or any identity, quantity, bracket, type, or worst-fill mismatch is `reconcile_required`
- strict `CLOSE`, `CLOSE_PARTIAL`, and `MODIFY_SL` mutations use the same full attestation rule after `OrderClose`/`OrderModify`: the ACK carries the target ticket and selected broker actuals, including mutation quantity, exact remaining lots, close time, and resulting SL as applicable. Full close requires zero remaining lots plus positive broker close time; protective intent does not relax post-mutation evidence
- `failed` and `duplicate` are terminal only with no positive ticket and explicit `mutation_state=not_attempted`. A positive ticket, `attempted`/`unknown` mutation, missing post-ticket truth, or semantic mismatch normalizes to `reconcile_required`; it blocks new entries while exact-owner protective handling remains available
- command rows persist typed ACK policy, schema, ticket, mutation state, and terminal-safety evidence in the same transaction as the command event and runtime ACK counters. Entry uncertainty reads those typed fields rather than casting legacy JSON; pre-migration or malformed terminal rows therefore remain fail-closed until reconciled
- the EA creates one stable `producer_instance_id` in terminal-local MQL Files using write/flush/promote/readback verification and fails initialization closed if it cannot load durable identity; the ID survives EA restart and scopes durable ACK replay without placing credentials in the file
- poll and ACK authenticate with `bridge_command_token.txt`, carry the URL-safe consumer identity, producer instance ID, terminal lease scope, credential generation, and exact bridge protocol, and atomically renew `bridge_consumer_lease` in the runtime database. The same full identity may resume/replay idempotently; a fresh lease held by another producer instance, even with the same credential triple, returns `409` and cannot poll, acknowledge, or publish broker truth
- the EA does not invent an `account_0` namespace: account number, account server, endpoint, Magic, and terminal data path are pinned once all required identity is available. Startup remains command-fenced while identity is unavailable, and any later account/server/endpoint/Magic/terminal drift keeps polling fenced while replay and deinit continue using the original pinned scope
- every MQ4 heartbeat reports `broker_account_mode` (`demo`, `contest`, `real`, or `unknown`), a non-reversible `broker_account_scope` derived from account number + server + Magic together with its schema/version, `broker_account_magic`, raw `broker_server`, raw `broker_company`, raw `broker_account_currency`, producer instance ID, credential/lease identity, and protocol; account number is never emitted. The bridge resets all identity fields before parsing, derives `broker_venue_id=ig_mt4` only when both server and company exactly match the explicit IG allowlists, and leaves venue/currency empty when evidence is absent rather than inferring either. A heartbeat market-source rollover clears the prior producer's positions, symbol specs, readiness, and associated source stamps before accepting new truth
- only an explicit plain-text heartbeat or JSON report with `report_type=heartbeat` may refresh bridge liveness or account identity; generic JSON reports such as `positions_snapshot` can update their own data but cannot keep a stale heartbeat or prior broker attestation alive
- `/v2/state` and `/v2/ready` expose `entry_configuration_ready` for static rollout admission and a separate dynamic `new_entry_ready`; the latter is true only while the effective signed-validation authority is enabled in `live` mode with a positive revision, runtime and queue are enabled, its expected `account_mode` matches current state, the broker mode and account scope are freshly attested, execution reconciliation is not account-wide, and at least one member of the scope-v3 exact ordered 22-symbol scalp scope has fresh MT4 transport, broker-market-event, signal, contract, and conversion evidence. `execution_uncertainty_present`, `execution_uncertainty_scope_contained`, and `execution_uncertainty_blocked_symbols` distinguish a contained quarantine from a clear book. `production_scalp_any_pair_ready` drives entry readiness, while `production_scalp_all_pairs_ready` is all-pair health telemetry and does not suppress an otherwise ready symbol. The ordered per-symbol readiness vector and aggregate booleans must agree or readiness fails closed. Effective empty scopes and zero budgets remain empty/zero rather than falling back to configuration. `new_entry_blocking_reasons` names the current owner of a stop.
- protective-management readiness is not entry readiness: `new_entry_ready` remains false. After invalid signed validation, the scalp runtime may publish operational readiness only after the revoked historical authority and exact-22 EXIT-only zero-budget egress contract is active; each position still requires its exact durable entry plus successful ACK or fresh authoritative snapshot join before `CLOSE` can enqueue or poll
- startup and every timer replay the durable outbox directly to `/v2/commands/ack`; replay never enters command handling. Timer replay is bounded to four files and rotates across pending files so one non-2xx record does not prevent attempts for other records
- the EA removes an ACK file only after HTTP 2xx. Transport, auth, unknown-command, invalid-transition, schema, and server failures remain queued and visible; temporary promotion failures are recovered on startup/timer, and deinit performs a final flushed persistence pass
- while any ACK is queued, staged, or not yet durable, the EA fences `/v2/commands/poll`. This prevents a delivered command from being re-polled and broker-executed while its outcome is awaiting reconciliation
- the outbox is capped at 512 persisted files with one slot reserved before polling; capacity or persistence failure is fail-closed and shown in the EA dashboard/log
- terminal replay relies on semantic identity, not status alone. An ACK whose effective status, mutation state, ticket, actuals, and attestation are exactly equal to the durable terminal outcome returns HTTP 200 with `idempotent: true`, appends no duplicate terminal event, and does not increment trade telemetry; a contradictory late or replayed outcome escalates the command to sticky `reconcile_required` rather than replacing broker truth. An exact attested late ACK may resolve a delivered command whose queue TTL elapsed
- scalp boot, egress disable, and startup-failure cleanup preserve queued exposure-reducing commands while still expiring queued entries and quarantining delivered uncertainty. An expired reducer with `delivered_count=0` may be resurrected only by the identical command identity and complete immutable business payload; any payload drift or evidence of prior delivery is rejected
- BUY/SELL lot size is immutable after Python risk approval: the EA accepts it only when it is finite, positive, within the live broker `MODE_MINLOT`/`MODE_MAXLOT` bounds, and exactly on `MODE_LOTSTEP`; it rejects instead of rounding or clamping
- strict partial closes preflight the one addressed broker ticket before `OrderClose`; legacy `ELBridge` partial closes retain their multi-ticket preflight. Every close amount and any ticket remainder must be exactly executable, and closed lots may never exceed approved `close_lots`
- BUY/SELL requires finite positive absolute `sl` and `tp_price` at the EA boundary. A BUY requires SL below bid and TP above ask; a SELL requires SL above ask and TP below bid. Broker stop-level distance is checked immediately before every `OrderSend`, including retries
- `MODIFY_SL` is tightening-only at the EA boundary: BUY stops must move strictly up and SELL stops strictly down, except that an absent broker stop may be initialized

## State Handshakes
- bridge stores authority, recovery, and operational runtime patch fragments
  in DB plus in-memory tick caches. Decision telemetry is append-only in
  `decision_snapshots` and is joined only when serving `/v2/state`, keeping the
  command-admission and operator-safety row lean.
- the EA may deliver the same quote on every timer, but only a changed `source_event_token` or changed bid/ask/mid is a broker market event. The first source token after bridge boot is a non-fresh baseline; duplicate receipts update transport telemetry only and are neither persisted as market ticks nor appended to live bar history
- the scalp loop evaluates ticks for exactly its 22 strategy symbols. Direct or inverse crosses needed to translate quote currency into the attested account currency are accepted only as named market-data extras and cannot become strategy candidates or executable pairs
- the MT4 market-data provider's canonical quote normalization must retain the transport and broker-market-event fields at the top-level runtime tick interface (and in provider metadata). Dropping them is a fail-closed integration fault: the API may be fresh while runtime entry admission correctly reports the identity missing
- runtime feature buckets use the last confirmed market-event receipt, not HTTP receipt time. New non-paper entries fail closed per pair on missing, baseline-only, or stale market-event evidence; paper flow and management of an existing position are unaffected
- final entry authorization reads the selected symbol and any required account-conversion quotes as one statement composed of per-symbol indexed latest-row seeks. It preserves exact authenticated market-source predicates and timestamp-plus-row-ID ordering without ranking the unbounded historical tick set on every enqueue and poll recheck.
- every broker positions payload is stamped at receipt with a unique `positions_snapshot_token`, bridge-clock `positions_snapshot_received_at`, `positions_snapshot_source`, source timestamp, and canonical authenticated market-source object/ID. Reconciliation uses the trusted bridge receipt time to order snapshot evidence against command submission and terminal updates; symbol containment additionally requires the broker source time to be newer so a delayed/replayed payload cannot release an account-wide fence. Reconciliation exposes the current source and whether the snapshot source matches it
- symbol specs expose the broker `trade_allowed` flag and a strictly positive price-unit `tick_size` from `SYMBOL_TRADE_TICK_SIZE` (never raw point-count `MODE_TICKSIZE`), plus point/digits/lot/stop/freeze/tick-value fields under the same authenticated source
- the runner carries the last-seen token across cycles and initializes it from pre-boot state. Only a different non-empty token sets `positions_snapshot_advanced`; the same persisted snapshot therefore cannot be reused as proof after a restart
- pending partial state and the exit-command ledger survive in `runtime_diag.managed_position_state` with recent-exit, campaign, and bounded sleeve history. Startup restores that state and hydrates only durable command rows changed after `max(managed_state.saved_at, runtime_last_cycle_ts)`, recovering the enqueue-to-state-patch gap without replaying older outcomes
- runtime state exposes `live_command_admission`, broker account attestation, and entry-ratio evidence counts/status; the ratio numerator counts only newly `queued` commands or duplicates backed by existing `queued`/`delivered` records, never rejected or failed attempts, and zero approved/accepted entries is `insufficient_evidence`
- while runtime is not ready, the EA backfills completed M5 broker bars in bounded batches; the bridge merges them with live tick aggregation so startup can rebuild causal M15/H1/H4/D context without accepting stale features
- the EA's sole scheduled positions producer is the versioned authoritative JSON snapshot. Its envelope binds the snapshot to broker account scope/schema/version, and every row includes logical and broker symbol, ticket, Magic, raw order comment, SL, TP, lots, prices, and open time; legacy text reports cannot overwrite it
- the command boundary does not infer ownership from symbol after restart. Production-scalp recovery starts from `managed_entry_command_id` and the exact durable BUY/SELL primary-key row, preserves that entry's full admission-mode/account-mode/generation/boot/admission-identity/engine/config/venue/scope/Magic/owner binding across later generations and boots, and then requires either its successful broker ACK or a fresh authoritative ticket/Magic/comment position join. Every resulting management command carries that historical identity. Ambiguous, stale, foreign, or unjoined positions remain quarantined while broker-native SL/TP stays active
- dashboard route fetches a verified state source, pins dependent reads to that exact bridge, and normalizes it into a stable client contract
- ops scripts use `/v2/ready` and `/v2/state` for health gates
- runtime and dashboard verify the exact reachable bridge through `/v2/handshake`; compatible minor/patch drift warns, while transient handshake failures are retried
