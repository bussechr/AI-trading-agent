## Start Order

- `_env.bat`: shared environment and bundled-interpreter resolution
- `01_sync_python.bat`: on a build/development host, install the filtered non-editable runtime distribution; in package mode, verify the bundled interpreter without importing repository source
- `02_sync_node.bat`: install the exact `pnpm-lock.yaml` graph, run the dashboard dependency/config doctor, and create a production build whose Next gate executes ESLint and TypeScript validation
- `00_preflight.bat`: in package mode, run `python -I -m fxstack.runtime.package_preflight`
- `20_start_bridge.bat`: run `python -I -m uvicorn fxstack.api.app:app --loop asyncio:SelectorEventLoop` and wait for `/v2/ready`; the selector loop avoids Windows Proactor reset-callback trace churn from the EA's short-lived HTTP sockets. Its collection-dependency-only `--background-if-absent` mode accepts a pinned repository Python and API-key file path, refuses when either the port or a matching bridge process already exists, and never enters the normal reset/kill path
- `19_start_mt4.ps1`: reuse or visibly launch the configured/IG MT4 terminal before runtime admission; it never stops the terminal
- `wait_for_mt4_broker_ready.ps1`: before runtime spawn, poll the authenticated loopback bridge for the exact demo/real account mode, account scope/Magic, IG venue, positive free margin, complete configured broker-symbol scope, and fresh heartbeat/ticks; timeout fails closed.
- `21_start_runtime.bat`: select the strategy-specific startup gate, validate the bounded cadence, and validate the strategy wrapper's exact content binding before any runtime reset. Runtime-native MTVCLC may cold-start only from an authenticated database-ready bridge with disabled egress and no active runtime; controlled replacement revalidates the same binding. The exact cadence is passed to isolated `python -I -m fxstack.runtime.runner`.
- `21_start_scalp_runtime.bat`: pin the production `mtvclc` family, exact ordered 22-symbol IG MT4 catalog, `scalp` plus `enter,exit` scopes, configured demo/real account mode, hash-pinned runtime-native cost contract, and one-second cadence. Qualified entries are immediate market BUY/SELL with broker SL/TP, pending orders forbidden, and maximum stop risk `0.5%` of current equity. The wrapper never starts MT4.
- `python -I -m fxstack.runtime.live_launch_authority_preflight`: read-only launch gate for every live path. It authenticates the configured release identity; external signed releases must match current service-owned authority, while runtime-native MTVCLC requires an authenticated inert bridge with egress disabled. A controlled `launch_all` replacement carries only the resulting content binding and must reproduce it after sync/stop. It never activates authority or starts a process.
- `21_run_scalp_runtime_task.ps1`: hidden, exit-code-preserving Scheduled Task trampoline for the exact `21_start_scalp_runtime.bat --run` launch and nothing else.
- `22_manage_scalp_runtime_task.ps1`: reversible current-user owner for `TradingAgentScalpRuntime`. `Register` creates or repairs and enables the exact Limited/InteractiveToken, current-user `AtLogOn`, restartable definition through the hidden PowerShell trampoline; `Start` enables if necessary and starts it. The former exact interactive `cmd.exe` action is recognized only as a safe migration identity. `Stop`, `Disable`, and `Unregister` still verify exact ownership, and `Stop` waits for Scheduler to report that the instance is no longer running. It never starts MT4 or reads credentials. The production package ships this owner; uninstall disables it before the egress-safe stack stop and unregisters it only after shutdown, refusing to delete an install root that an identity-mismatched task still references.
- `python -I -m fxstack.runtime.model_manifest_preflight`: model-stack-only read-only manifest, feature-contract, registry-provenance, and local-payload gate before runtime reset/spawn
- `22_start_dashboard.bat`: rebuild a missing or source-stale dashboard through the same lint/type-enforcing Next production gate, then start the Next.js production server
- `23_start_monitor.bat`: run the installed `fxstack.runtime.monitor` module under Python isolated mode
- `24_start_feature_push_worker.bat`: run the installed `fxstack.runtime.feature_push_worker` module to drain runtime feature-push intents into Feast
- `tools/capture_ig_mt4_m1_activity_resilient_v4.py` and `tools/check_mt4_tick_volume_collector_continuity_resilient_v3.py`: the v5 successor collection adapter and its no-network continuity inspector. They bind the frozen v4 adapter, exact v3 collector template, wrapper/base support, readiness-retry contract, continuity core, preregistration, producer, policy, and external output root to `collector-guard.identity.gap-v5.v1.json`. The inspector loads the reusable core into a private module namespace, so importing it cannot contaminate the public continuity-core module.
- `27_guard_mtvclc_collector_resilient_v3.ps1`: distinct gap-v5 `Health`, `AdoptRunning`, and `StartOrResume` boundary using `supervision-gap-v5`. It hash-pins the v4 collector adapter, its v3 template, inspector/core, producer, and preregistration tuple. `AdoptRunning` is available only for one exact existing writer after the exclusive lock is demonstrably available; duplicate or mismatched writers refuse. Every authority field remains false.
- `28_ensure_mtvclc_collection_dependencies.ps1`: explicit operator-invoked collection-only dependency check for the exact repository-owned bridge at `127.0.0.1:58710` and configured visible IG MT4 terminal. Before any start it validates source hashes, terminal/process ownership, listener command/ancestry/PID-marker identity, and the single API-key file path. It starts only a completely absent bridge through `--background-if-absent`, starts MT4 only when no terminal is running and an interactive desktop exists, never stops a healthy or foreign process, and admits success only after authenticated `/v2/handshake`, `/v2/ready`, and `/v2/state` prove IG-DEMO plus the exact ordered 22-symbol readiness vector. It installs no persistence and never starts the runtime or accesses command, evaluation, or trading paths
- `29_ensure_mtvclc_collector_resilient_v3.ps1`: hash-pinned full-lifetime gap-v5 task action. From zero writer plus unlocked/open-window Health it invokes `StartOrResume` synchronously and propagates the guard's final exit code, keeping task action -> guard -> collector ancestry alive for the whole collection lifetime while redirecting guard output to stable supervision logs. Recovery is explicit: one exact writer plus an available lock is synchronously adopted, one exact writer plus a held lock is reported as a detached supervisor and refused, and duplicate/mismatched writers fail closed; no branch kills a process.
- `29_register_mtvclc_collector_resilient_watchdog_v3.ps1`: explicit reversible preview/installer/starter/remover for the distinct `TradingAgentMtvclcV5Collector` full-lifetime task. Its recurring top-level PowerShell host is hidden. `Start` requires the exact enabled definition in `Ready`, zero COM running instances, and zero writer/unlocked/open-window Health before mutation. Success requires the unchanged task to remain `Running`, exactly one new Task Scheduler COM instance in numeric Running state, a transitioned `LastRunTime`, one exact action process created after the request and bound to `EnginePID`, exact action -> `StartOrResume` guard -> writer ancestry, and two identical healthy locked-writer samples at least one second apart. `LastTaskResult` is diagnostic only while live; `Ready` plus a writer is `orphaned_writer_not_task_owned`; timeout never stops anything. `Remove` refuses any non-Ready task, running instance, writer, or held lock. `IgnoreNew`, unlimited execution time, and repeating triggers provide recovery opportunities without spawning duplicates. Before the first Windows acceptance run, live COM/EnginePID ownership remained unproven; after any run, the exact current task/COM/process state and capture artifacts are authoritative. Success returns on caller stdout; no immutable operational supervision receipt is yet bound into the capture or handoff evidence.
- `29_preserve_mtvclc_capture.ps1`: operator-invoked collection-only durability check and append-only replica for one exact external preregistration/capture/guard identity tuple. Its strict family map accepts legacy v1/v2 only as `mtvclc_v1_preregistration_<sha256>.json` under the resilient-v1/watermark-v2 parents with the legacy capture and guard leaves; accepts runtime-bound-v3/v4 only with the gap-v3 preregistration/capture names and `collector-guard.identity.gap-v3.v1.json`; and accepts runtime-bound-v5 under `fxstack.scalp.mtvclc_preservation_filenames.v5` only with the same content-addressed gap-v3 wire names plus `collector-guard.identity.gap-v5.v1.json`. Mixed guard leaves are refused. It requires an explicit pre-existing backup root on a distinct volume, defaults to a 500 GB warning and 311 GB hard capture-volume floor, checks manifest and active-journal freshness from file metadata only, stability-probes closed chunk files, and copies the sealed preregistration, immutable guard identity, closed chunks, and content-addressed manifest snapshots without parsing any record. It categorically excludes the active journal, refuses destination identity conflicts, never overwrites or deletes backup data, and emits all authority fields false; this entrypoint is not installed or scheduled automatically
- `29_register_mtvclc_capture_preservation_task.ps1`: explicit reversible preview/installer/remover for the preservation boundary. Invocation defaults to non-mutating `Preview`; explicit Install uses current-user `AtLogOn` plus a 60-minute repeating trigger, while optional `AtStartup` mutation requires an administrator and uses the same current-user S4U identity, so the chosen backup root must be reachable noninteractively. Its recurring top-level PowerShell host is hidden. Its complete action pins the preservation script hash, exact preregistration/capture/backup paths, expected preregistration and guard hashes, drive, capacity, freshness, closed-file, and clock-skew policy; `IgnoreNew` and `StartWhenAvailable` prevent overlap and catch up safely. It never starts the task during registration, accepts no key or credential, never reads/evaluates evidence, and refuses overwrite or removal unless path, action, full arguments, owner marker, principal, trigger topology/repetition, and settings all prove the exact owned definition. To remove after the preservation script changes, supply the task's original `-PinnedPreservationScriptSha256`
- `tools/verify_mt4_tick_volume_capture_handoff_v5.py`: active post-window-only offline v5 audit of the exact sealed preregistration, gap-v5 guard identity, complete compatible gap-v3 manifest chain, every referenced chunk/row, authenticated source continuity, reservation-tail/finalization binding, edge coverage, and orphan-free chunk tree; it publishes an authority-free content-addressed inventory and refuses before the exclusive window end. The unversioned handoff remains historical compatibility only
- `90_stop_all.bat`: durably disable production execution authority and egress and quarantine queued commands before invoking `stop_owned_stack_processes.ps1`; shutdown uses process-tree semantics and must prove the configured bridge/dashboard listeners are gone before PID markers are removed, and it never stops MT4

`tools/preflight_active_models.py` is an external developer/build-host adapter for the same read-only validator. Production launchers never invoke it.

## Production Package Boundary

- The deployed Python surface is the filtered, non-editable `fx-quant-stack` distribution in bundled `site-packages`. The installer does not ship the raw `fx-quant-stack/src` tree, a repository CLI shim, or a repository feature-worker helper.
- Bridge, runner, feature-push worker, monitor, package preflight, and model-manifest preflight all execute from that installed distribution under `python -I`; there is no repository-source production fallback. Bridge and runtime implementation are fixed by those direct module entrypoints and expose no legacy implementation-selector environment variable.
- The runtime distribution contains inference, policy, risk, portfolio, persistence, API, monitoring, and read-only artifact-validation code. Runtime callers use `fxstack.mlops.local_artifact`, which can only resolve already-present payloads; the MLflow client and the remote-capable `fxstack.mlops.model_uri` module are forbidden. Training activation, registry mutation, research/backtest, replay/experiment, LLM/improvement, RL training environments, and the other write-side modules checked by `runtime_physical_isolation_errors()` are physically absent.
- `build_windows_installer.py` independently reruns the current physical-isolation probe, packages the filtered site-packages runtime, the exact source migration list, the canonical scalp launcher and its reversible Scheduled Task owner, the administrator-run database-boundary SQL, and only the exact local artifact and registry paths named by the active manifest. It ships neither a separate scalp shadow launcher nor raw artifact-run roots, `fx-quant-stack/scripts`, `fx-quant-stack/configs` (including the external training config), Python/Node synchronization launchers, the CUDA build-host check, the training aggregate monitor, training, activation, backtest, nor candidate/full-validation capability; the only shipped full-validation file is the nonzero quarantine stub reached by `launch_all.bat full`, and the installed app receives only `uninstall.ps1` from the external installer sources. Its isolated dashboard build never copies the checkout `.env` and receives only an allowlisted toolchain environment, so build-host credentials cannot be baked into Next output. The builder rejects duplicate, escaping, linked, and special tar members and ships only the three authoritative BridgeEA source files, so ignored local compiler output and migration caches cannot enter a release. The installer independently lists and validates the same relative `app/`-only, file/directory-only archive before extraction, proves the extracted app root, and only then stops an existing installation. The generated root marker prevents install/uninstall from recursively mutating an unrelated target. Upgrades mirror package-owned paths but merge rather than purge `fx-quant-stack/data` and exclude local `logs`, preserving the runtime database, bridge credentials, endpoint state, and operator snapshots. Installed Monitor shortcuts target the packaged `monitor_trading_agent.bat` helper rather than the excluded aggregate monitor.
- Installation is non-starting by default: payload extraction, ownership-safe mirroring, and shortcut creation do not invoke `launch_all`, MT4, the bridge, or the runtime. A direct PowerShell caller must pass `-StartAfterInstall` to opt into post-install launch; the normal EXE/folder installers leave startup to the explicit Trading Agent shortcut after signed authority and broker prerequisites are ready.
- Installer assembly owns its output through `.fxstack-installer-build-root`. It refuses filesystem roots, the repository or any repository parent, and every nonempty output directory without the exact marker before recursive replacement.
- The exact-22 scalp path has one canonical runtime. Demo and real select broker-account expectations but use the same engine, admission, signal, qualification, sizing, and execution code.

## Isolated Training And Activation

- Training, research, promotion, and activation run on an external build/research host before deployment. The numbered Windows batch files and the WSL GPU backtest pipeline invoke focused Python scripts directly; `src.trader` is not in these paths. The repository root has no second Python manifest, lock, requirements file, or console script; `fx-quant-stack/pyproject.toml` plus its `uv.lock` are authoritative. The root `src/trader` tree contains only a source-level allowlisted facade for advisory self-improvement research, offline security/weight checks, and Lean export; its parser has no runtime, bridge, live-data, database, training, activation, deployment, or operator verbs, and its duplicate runtime, decision, persistence, DTO, and protocol stacks are absent. Source-only calls are explicit and confined to isolated research documentation and tests. These scripts and their write-side dependencies are not production runtime entrypoints.
- Before isolated replay, `capture_ig_scalp_cost_model.py --capture-mode live` can seal at least 300 current unique events per symbol with the five-second gap bound. `--capture-mode db-history` instead opens only a proven read-only transaction, exports at least 100 persisted unique events per symbol from the currently authenticated source over at least 300 seconds, records intersample gaps as telemetry, and requires fresh full-scope endpoint events before and after the history read. Neither mode reads commands or exports credentials; the issuer rechecks its mode-specific JSON/NPZ contract.
- MTVCLC evidence and release preparation stay off the production host. A future operator may use the v5 preregistration/handoff/evaluator chain only after its independent fixed 180-day window and only on the physically isolated research host. `tools/mtvclc_validation_release_v5.py` remains public-first and key-last for authority-free evidence-v3. A distinct later `tools/mtvclc_runtime_release.py prepare` requires the exact content-addressed v5 preregistration and produces only an issuance-request-v2 after its body/artifact hashes match signed evidence, its sealed whole engine matches the measured engine, and its BUY-at-ask/SELL-at-bid immediate-market policy forbids both pending forms. `issue` repeats those checks before first private-key access and emits only an outer-v2 certificate/bundle plus the v1 registry. Neither tool generates a key, installs a bundle, starts a runtime, or authorizes a real account or unsigned demo entry.
- MLflow, deep training/inference, OTLP export, and Dukascopy download dependencies are opt-in through the external `external_mlops`, `deep_inference`, `observability`, and `market_data_download` extras. Production retains only the lightweight OpenTelemetry API and excludes the offline downloader package; the packaged xgb-only environment installs none of those extras.
- `25_monitor_everything.ps1` is an external build/research-host aggregate view because it inspects training and candidate state; the packaged monitor helper calls the installed `fxstack.runtime.monitor` instead.
- Keep a candidate run out of the active data and artifact trees with `FXSTACK_TRAIN_RAW_ROOT`, `FXSTACK_TRAIN_FEATURE_ROOT`, `FXSTACK_TRAIN_LABEL_ROOT`, `FXSTACK_TRAIN_ARTIFACT_ROOT`, and `FXSTACK_TRAIN_REGISTRY_ROOT`. The shorter `FXSTACK_ARTIFACT_ROOT` / `FXSTACK_REGISTRY_ROOT` names are not launcher inputs.
- Use `FXSTACK_TRAIN_PAIRS` to select the pair jobs for a candidate batch without narrowing `FXSTACK_PAIRS`, which remains the feature and directional-belief context universe. When omitted, the training selector defaults to the complete configured universe. The batch trains the one global directional-belief bundle in the first successful pair job only, then passes `--no-with-belief` to every remaining pair; `FXSTACK_TRAIN_WITH_BELIEF=0` disables it for the complete batch.
- Set `FXSTACK_TRAIN_ALLOW_INGEST=0` for point-in-time or otherwise isolated training. This makes missing snapshot inputs fail closed instead of rebuilding them from the project-wide raw tree.
- Deep-model launchers `16_train_swing_transformer.bat`, `17_train_intraday_tcn.bat`, and `18_train_deep_stale.bat` consume the same artifact, feature, and label roots.
- The WSL full-backtest pipeline does not repeat `train_deep_stale.py` after `train_all.py`; each pair job already owns that stale/force decision and records it in the bundle evidence.
- Use `FXSTACK_FORCE_RETRAIN=1` after feature-contract or numerical-integrity changes. Set `FXSTACK_TRAIN_WITH_BELIEF=0` when reusing an already validated cross-pair belief bundle.
- Before leaving a long batch unattended, inspect the external training process generated by `13_train_all.bat` and confirm every isolated root plus disabled ingest appears.
- Validate and activate the candidate registry externally with `FXSTACK_ACTIVATE_REGISTRY_ROOT` and `FXSTACK_ACTIVATE_MANIFEST`; activation rejects every registry whose promotion status is not `eligible`. Keep the candidate manifest outside `fx-quant-stack/artifacts/active_models.json` until validation passes.
- Canary monitoring computes entry evidence from accepted queue records, not submission attempts: accepted means newly `queued` or a duplicate already `queued`/`delivered`. Zero approved and zero accepted entries is `insufficient_evidence`, not a passing ratio. Evidence carries its observation timestamp and stage index/percentage; advancement clears it, and the next stage requires a new runtime observation after the ramp. `advance_canary_stage` therefore cannot recycle one passing sample across exposure levels.
- Phase 5 pre-canary evidence is bound to one exact pair, release bundle, model set, active-manifest hash, and artifact-set hash. Advisory causal-research output is rejected. Run an external harness with `python -m fxstack.backtest.harness.lean` or `python -m fxstack.backtest.harness.nautilus` plus `--execute --model-manifest ... --economic-report ... --manifest-output ...`, then normalize it with `tools/assemble_phase5_economic_evidence.py`; planned or hand-weakened manifests are rejected. Runtime authority requires the actual candidate for at least 24 hours in broker-emission-disabled shadow posture with loaded lifecycle models, healthy samples, and zero emitted entry commands. Finalization separately requires distinct 15-minute and 24-hour artifacts/windows. Gate reload and finalization rehash the referenced files and derive gate state rather than trusting stored pass booleans.
- Before installer assembly, use `tools/stage_candidate_registry.py` to copy only validated immutable artifacts into an ignored repository-relative `fx-quant-stack/artifacts_shadow/...` handoff and rebase their registry references. Rerun candidate activation and read-only preflight against that staged registry before replacing the active manifest.
- Assemble the installer only after activation has produced the immutable active manifest, registry provenance, and content-digested artifacts consumed by production preflight. The deployed package can validate and load that handoff but cannot activate or rewrite it.
- End-to-end release proof runs the exact candidate on the external validation host or VM in broker-emission-disabled shadow posture. Its database, bridge, credentials, feature/raw roots, registry, logs, and rollback control stay outside the production trust domain. A deployed scalp path receives only the externally signed, content-addressed validation bundle and public verification key through the quarantine import workflow, regardless of broker account mode.
- Research output remains advisory. An explicitly selected, authenticated, unexpired, non-revoked `signed_validation` release is mandatory for every live production-scalp launch, including broker-attested IG-DEMO.
- The installed package is measured as a complete link-free relative-file/SHA-256 inventory. Signed build provenance must match that measured Merkle digest and the package root actually executing. The signed runtime-config digest classifies every public setting exactly once; endpoint, secret, machine path, training, and observability exclusions are explicit rather than substring-based.

## Endpoint And Auth Contract

- `launch_all.bat live [EQUITY] [BRIDGE_PORT] [DASHBOARD_PORT]` selects both endpoints once before startup and routes by strategy family. Every live path first validates current signed authority and captures its exact content binding before Python sync or any stop/restart; missing, expired, revoked, drifted, or strategy-mismatched authority leaves that stack untouched.
- `launch_all.bat` without an explicit action prints usage and starts nothing. The launcher never treats a bare or double-click invocation as permission to start MT4 or any broker-connected service.
- `launch_all.bat endpoints [BRIDGE_PORT] [DASHBOARD_PORT]` performs only the bind checks and prints/persists the resolved URLs; it starts no service.
- `resolve_stack_endpoints.ps1` verifies actual loopback binds, so active listeners and Windows excluded TCP ranges are both rejected. Omitted ports may move upward to the first bindable port; explicit command-line ports are strict.
- The selected ports are persisted in ignored `logs/active_stack_env.bat`. Active values override installed defaults, so `_env.bat`, status, monitor, stop, bridge, runtime, and dashboard consume the same endpoints on later invocations. `_env.bat` never reads the retired `active_candidate_env.bat` artifact. `90_stop_all.bat` removes both active endpoint state and any stale candidate artifact after cleanup.
- Live startup persists endpoint state after any side-by-side Python environment switch, because that switch stops the previous owned stack and clears stale endpoint state.
- `_env.bat` derives `MT4_BRIDGE_URL`, `TRADER_BRIDGE_URL`, and `TRADER_DASHBOARD_URL` from those endpoints unless an operator supplied an explicit URL.
- Bridge auth stays enabled by default. If no credentials were supplied, separate 256-bit keys are generated once in ignored `logs/bridge_api_key.txt` and `logs/bridge_command_token.txt`. The general key authenticates telemetry/state traffic; only the distinct command token can poll or ACK. `_env.bat` also pins the command consumer identity, terminal-wide lease scope, token scope, credential generation, and bounded lease TTL. `24_deploy_bridge_ea.bat` installs those values as non-journaled terminal files while MT4 is stopped.
- Runtime launch posture is resolved by the selected launcher with `--validate`. After `_env.bat` identifies `FXSTACK_ENTRY_STRATEGY_FAMILY=mtvclc`, `launch_all.bat live` routes validation, model-validation dispatch, and background start through `21_start_scalp_runtime.bat`; other families use `21_start_runtime.bat`. Every live run/background repeats the signed-release check before resetting or spawning a runtime process; validation-only modes do not mutate processes.
- `00_preflight.bat` package mode runs the installed `fxstack.runtime.package_preflight` module. It rejects missing required dependencies, invalid settings/database posture, MLflow, or any forbidden training/research/write-side module visible inside the isolated interpreter.
- `21_start_runtime.bat --validate-models`, `--run`, and `--background` run the read-only active-model preflight from the non-editable, research-pruned installed package under Python isolated mode before any runtime process reset or spawn for the model strategy family. The gate requires every configured pair in `FXSTACK_PAIRS`, `promotion_status=eligible`, the current feature contract, matching local registry provenance where applicable, and valid local artifact payload digests. A `pair=GLOBAL` scope is accepted only for the cross-pair directional-belief component; it never relaxes contract or payload checks. The preflight never downloads, deserializes, trains, promotes, activates, writes the manifest, or touches the runtime database. `mtvclc` skips this model-specific gate and instead verifies the outer-v2 IG-DEMO runtime release, revocation registry, embedded evidence-v3, exact v5 preregistration and sealed-engine binding, generation/config, exact 22-symbol cost mapping, immediate-market contract, and 44-cell qualification surface.
- Direct `python -I -m fxstack.runtime.runner` invocation cannot bypass startup admission: Python accepts only the literal `--instance-id baseline`, repeats settings validation, requires explicit live arming and scopes, proves the complete forbidden-module set is absent, and enforces the selected strategy-family gate before bridge checks or `RuntimeService` access. The model family requires binding structure-timing/chase, uncertainty, belief, campaign, and capital-governance settings plus the read-only model preflight. Exact-scope `mtvclc` is IG-DEMO-only and requires its separately signed public runtime release plus revocation admission. The feature-push worker enforces the same baseline-only identity. The production settings and runner contain no adaptive observation-twin switch or baseline-ranking comparator.
- Physical isolation means the installed production interpreter contains no research/write-side modules or research credentials, not that research is unable to communicate. Advisory artifacts can cross the boundary as data. Production startup and execution do not depend on research availability or approval; the singleton bridge consumer, terminal identity lease, and distinct poll/ACK token still fence the broker channel.
- `ops/windows/provision_live_db_boundary.sql` is the packaged, administrator-reviewed, idempotent local role reduction for the default deployment: it removes cluster-wide creation authority from `fx` and creates a separate `NOLOGIN` research marker without granting membership. Run it through `psql` as a PostgreSQL administrator; the installer and runtime never auto-execute it, and the runtime account cannot self-authorize this boundary.
- With neither strategy-specific override supplied, `FXSTACK_START_PROFILE=staged_safe` deterministically resolves to `FXSTACK_AGENT_MODE=shadow`. The production runtime rejects `FXSTACK_START_PROFILE=paper` because the simulated execution adapter is physically absent. Any explicit profile/mode mismatch fails before spawn. `_env.bat` remains generic; `21_start_scalp_runtime.bat` pins the exact strategy/catalog/scopes and expected IG-DEMO account mode but never creates live/live/armed or shadow-off posture.
- Every live posture requires `FXSTACK_START_PROFILE=live`, an explicitly matching `FXSTACK_AGENT_MODE=live`, `FXSTACK_LIVE_ARMED=1`, an explicit `FXSTACK_LIVE_EXPECTED_ACCOUNT_MODE=demo` or `real`, explicit non-empty pair/sleeve/intent scopes, and the signed-release preflight. Capital governance, the code-owned `<=0.5%` current-equity scalp immediate-trade cap, other hard-risk limits, execution egress, queue kills, broker account attestation, command authority, reconciliation, and ACK fences remain binding.
- The shipped Windows adaptive scope defaults to `FXSTACK_ADAPTIVE_PLAYBOOKS=trend_pullback`, but entry authority belongs to the intelligent enter-vs-abstain comparison. The former fixed trend-probe confidence and lot-scale settings are absent; the selected action margin scales requested lots continuously before final risk approval.
- After model load, Python live startup applies the explicit production operator scope and requires every configured pair to have an active pair-allowlisted `live` rollout with positive budget. The intent allowlist must contain only supported intents and include `enter`, plus `exit` and `reduce` when lifecycle actions are enabled and `tighten_stop` when adjustment actions are enabled; otherwise startup raises `live_command_admission_blocked` before trading begins. The scalp branch constructs its own exact-scope live rollout and binds it to the selected `admission_mode`, expected `account_mode`, current boot, and authority revision
- Production rollout checks apply only to new `enter` authority. Protective lifecycle actions do not depend on entry budget, but they still require the explicit production intent/pair scope for the current runtime boot and remain subject to runtime/queue kills, governance, risk, reconciliation, and broker validation. `CLOSE_ALL` remains a production emergency action.
- Every broker verb—including protective actions and `INFO`—is fenced at both database enqueue and MQ4 poll against the acknowledged authority generation, admission mode, account mode, boot, revision, and explicit scopes. Missing, pending, rejected, expired, superseded, or drifted authority returns an empty/quarantined poll result; there is no status-command or old-process bypass.
- Live `enter` also requires a fresh MQ4 heartbeat attesting a known `demo` or `real` account mode and a non-empty account scope derived from account number, server, and Magic. `contest`, `unknown`, missing, or stale attestation blocks the entry; `FinalEntryApproval` carries the mode/scope and service enqueue rereads state to reject identity drift. This entry-only attestation gate does not suppress protective commands.
- Live validation also requires finite positive sizing and hard-risk limits before any process reset or spawn. The generic lane defaults scale at `0.00001` lots/USD, cap each order at `0.10` lots, and cap gross/net lot exposure at `0.30`/`0.20`. Those cross-instrument lot ceilings are deliberately non-binding in the scalp launcher because they can under-use a valid cash-risk budget and do not compare equivalent risk across instruments. Scalp broker-contract sizing instead chooses the largest broker-valid lot that fits the `0.5%` current-equity stop-risk budget, broker maximum, and available margin, rounded down to the broker lot step; one position per symbol and six total positions remain binding. The shared `5%` drawdown stop remains active. The cash-risk proof is rechecked against current equity and contract/conversion state at sizing, enqueue, and broker poll; provider and EA validation then preserve the approved lots/SL/TP and contract geometry. `validate_runtime_risk_limits.ps1` requires the managed-runner TP multiple to be either disabled at `0` or finite and at least `1R`; Python startup repeats the contract through `Settings.validate_for_startup()`.
- With lifecycle actions enabled, `_env.bat` defaults `FXSTACK_MANAGED_RUNNER_TP_R_MULTIPLE=0`, disabling the former forced `4R` target that measured materially worse than the available geometry. The generic baseline uses `FXSTACK_ENTRY_STOP_ATR_MULTIPLE=3.0` and `FXSTACK_ENTRY_TAKE_PROFIT_ATR_MULTIPLE=1.5`, yielding `max(1.5*ATR, 0.5R)` while risk-based sizing reduces lots for the wider stop. Strategy-specific signed authority may bind stricter geometry; position-signature-stable lifecycle state, final partial materialization, and final lifecycle risk approval own ordinary partials and exits.
- The removed MCP/OpenClaw operator plane has no launcher or runtime setting. Remote LLM and external-tool access remain disabled unless explicitly enabled for an implemented isolated workflow.
- Production operations expose no offline self-correction launcher. The former continuous supervisor is removed; self-improvement evidence is produced only in a physically isolated research environment and has no runtime-database registration path.
- The retired `TradingAgentWeeklyFullRetrain` path is removed end to end: no auto-retrain tool, batch wrapper, registrar, setting, or installer hook remains. Retraining and activation require an explicit external pre-deployment invocation; the uninstaller retains only identity-safe cleanup for an exact historical weekly task left by an older installation.
- For isolated audits, set `FXSTACK_SKIP_INSTALLED_ENV=1` before calling any Windows entrypoint. `_env.bat` then skips the optional credential-bearing `installed_env.bat` while still loading active endpoint state and process-supplied/default settings. This lets a guarded caller enforce shadow + SQLite + feature-push-off values without machine overrides.

## Single Production Instance

- The production host admits exactly one runtime/bridge/feature-worker stack with instance ID `baseline`. Batch launchers and both installed Python CLIs reject every other identity before database or process mutation.
- `24_start_candidate_stack.bat`, `30_fast_gate_15m.bat`, `31_shadow_24h.bat`, and `40_full_scale_e2e_validation.bat` are nonzero quarantine stubs. They cannot start, observe, roll back, or stop a same-host candidate.
- `find_owned_instance_processes.ps1` remains a read-only ownership selector so shutdown can recognize and remove a stale pre-quarantine repo-owned process. It does not authorize starting another instance.
- `90_stop_all.bat` first runs `python -I -m fxstack.runtime.execution_egress_control --reason operator_stop_all`. No taskkill occurs unless that command confirms egress disabled, production runtime authority killed, and the command quarantine committed. Advisory release/twin state is irrelevant to shutdown success. `stop_owned_stack_processes.ps1` then admits only root-owned workers or workers bound to a fresh launcher PID marker, kills their full process trees, and waits until no admitted worker or configured listener remains. Stale PID reuse is rejected by comparing process creation time to marker write time. Process cleanup is repository-scoped; the global `python.exe` kill escape hatch is absent.

## One-Time Retired Candidate Cleanup

Perform this once on every former dual-stack workstation before treating it as a production host:

1. Identify the retired candidate terminal by its exact terminal data path, broker account/server, Magic number, and bridge URL. Reconcile open positions and verify that no pending orders exist for that exact account before changing the terminal.
2. In that identified terminal only, disable AutoTrading, detach/disable the candidate BridgeEA, and remove any candidate auto-start shortcut, Scheduled Task, or service. Do not use `taskkill /im terminal.exe`; the Windows scripts intentionally never kill arbitrary MT4 terminals.
3. Revoke the retired candidate bridge credential at its consumer, rotate the production bridge API key, update the production EA and `installed_env.bat` together, and verify old-key requests are rejected before re-enabling the production EA.
4. Run `90_stop_all.bat` to durably revoke production execution egress and remove repo-owned processes plus stale `logs/active_candidate_env.bat`. Archive the retired candidate database/data/log roots offline; do not mount them into production.
5. Restart `launch_all.bat live` only after the selected strategy's signed release is active. Verify one baseline runner, one bridge, one feature worker (when enabled), the intended MT4 account/server/Magic heartbeat, and no traffic from the retired candidate terminal. Every live path, including exact-22 IG-DEMO scalp, refuses before sync or stop when signed authority is absent, invalid, expired, revoked, or drifted.
